## Scope and required code

Milestone 1 is the first milestone in the repository assessment: manual acceptance of the existing client. The game features already exist. No new feature or production-code implementation is required if all checks pass. Implement only fixes for failures reproduced during the steps below; there is no known defect being asserted by this plan.

Keep TCP, encoder/parser/framing, network timers, and the server for later milestones. Tests that require `TODO[EP-REDE]` stubs should still pass at the end of this milestone.

## Global constraints

- Python 3.12+; standard-library runtime; Linux/WSL curses.
- Keep project-owned Python comments and docstrings in Portuguese.
- Engine must not import curses, sockets, or session adapters.
- Preserve attack → board snapshot → local defeat publication order.
- Preserve injectable clocks and separate piece/garbage RNGs.
- Exactly two players and eight protocol message types; no additional multiplayer features.
- Preserve the existing network thread/queue scaffold and explicit stubs; never substitute FakeSession in network mode.
- Keep vendored skills, license, and provenance unchanged.

## 2. Accept the menu and practice mode

Run in an actual interactive terminal, initially at least 80 columns × 28 rows:

```bash
PYTHONPATH=src python3 -m tetris_client
```

- [ ] Edit the nickname with typing and Backspace; select Practice and verify the local board header uses the chosen name. Nicknames permit 1–20 ASCII letters, digits, or underscores.
- [ ] Verify left/right movement and soft drop stop at collisions and board boundaries.
- [ ] Verify ↑/X clockwise, Z counterclockwise, and A 180° rotation; check lowercase and uppercase letters. Rotations have no wall kicks.
- [ ] Verify C holds once per lock and the held/next pieces are readable. A second hold before locking must do nothing.
- [ ] Verify Space drops and locks immediately, while normal landing allows adjustment before locking.
- [ ] Play long enough to observe the displayed lock delay fall from 800 ms to 750 ms after 30 seconds of active play. Movement and rotation must not reset a piece's lock deadline.
- [ ] Pause with `p`, wait, and resume. Physics and lock-delay progression must remain frozen during the pause.
- [ ] Complete a line and check cleanup and score. The score table is 100/300/500/800 for 1/2/3/4 lines. Use deterministic engine tests for hard-to-create multi-line arrangements rather than requiring every arrangement manually.
- [ ] Reach top out and verify “Fim do treino”; physics must stop.
- [ ] Quit with `q`, start a fresh practice process, and verify score, garbage, and hold reset.

## 5. Implement fixes only for reproduced failures

Use this map to choose the smallest responsible component:

| Failure | Implementation location | Existing regression-test location |
| --- | --- | --- |
| Movement, collision, gravity, clearing, score, garbage, top out | `src/tetris_client/engine.py`: `move`, `soft_drop`, `hard_drop`, `tick`, `_lock`, `_spawn` | `tests/test_client.py` |
| Lock deadline or pause timing | `src/tetris_client/engine.py`: `lock_delay`, `_touch_ground`, `pause`, `resume`, `tick` | `tests/test_menu_and_delay.py` |
| Hold or rotations | `src/tetris_client/engine.py`: `hold`, `rotate`; UI key mapping in `_run` | `tests/test_hold_and_rotation.py` |
| Drawing, terminal size, colors, labels, input/menu | `src/tetris_client/ui.py`: `_render`, `_board`, `_palette`, `_menu`, `_run`, `run` | Screen substitutes in `tests/test_menu_and_delay.py`, `tests/test_hold_and_rotation.py`, and `tests/test_network_entrypoints.py` |
| Readiness, pause permissions, result handling, output ordering | `src/tetris_client/app.py`: `start`, `ready`, `update`, `action`, `_publish`, `close` | `tests/test_client.py` |
| Demonstration event ordering or injected outcomes | `src/tetris_client/session.py`: `FakeSession` | `tests/test_client.py` |
| CLI validation, exit codes, network-unavailable reporting | `src/tetris_client/__main__.py`: `main`; `src/tetris_client/ui.py`: `_run` | `tests/test_network_entrypoints.py` |

For each confirmed behavior defect:

1. Record exact reproduction steps and expected behavior from the specification.
2. Identify the responsible code path using systematic debugging.
3. Add a deterministic regression test to the relevant existing test module; use injected clocks/RNGs or the existing screen substitute as appropriate.
4. Run the targeted test and confirm it fails for the reported reason.
5. Implement the smallest fix, preserving the module boundaries and existing interfaces.
6. Run the targeted test, then the full unittest suite.
7. Repeat the original manual reproduction in the real terminal and record the result.

For purely visual issues, record before/after evidence and manually check the actual terminal; do not add tests that only repeat rendering implementation details.
